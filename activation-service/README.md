# AppStore+ — персональная активация и Telegram-бот

Это исходники сервиса для подготовки и тестирования, а не уже работающий сервер. Токен бота, домен HTTPS и персональный сертификат ещё не подключены. Существующий @appleipastore_bot не изменяется.

## Что готово

- Бот отвечает только в личном чате отправителю: /start, /install, /status, /support. Доступ выдаётся по Telegram numeric ID, а не username. Самостоятельно активировать доступ или назначать чужой Telegram ID нельзя.
- Администратор локально регистрирует готовую пару p12/mobileprovision. Проверяются пароль, соответствие пары, наличие UDID, срок профиля/сертификата и конец доступа. Бот не получает p12/пароль.
- На диск сертификаты попадают в SQLite в AES-256-GCM; мастер-ключ хранится отдельно в переменной среды. Сессионные токены и коды в базе хешируются.
- Персональный ресурс добавляется к UNSIGNED IPA до подписи. Не нужно компилировать магазин заново для каждого клиента. Утилита не подписывает IPA и не регистрирует UDID в Apple.
- На первом запуске приложение генерирует P-256 ключ, привязывает активацию к его открытому ключу и получает сессию. Повторные запросы подписываются с timestamp и одноразовым nonce; скопированного session token недостаточно.
- Сертификат скачивается по HTTPS, импортируется в существующий движок, выбирается основным; данные доступа отображаются отдельно.

## Что требуется для запуска

1. Python 3.11+ и `pip install -r requirements.txt`, OpenSSL.
2. Сгенерировать APPSTORE_MASTER_KEY (32 random bytes, base64). Сохранить в защищённой конфигурации; потеря ключа делает сертификаты в базе нечитаемыми. Не менять между перезапусками.
3. Домен HTTPS и reverse proxy к 127.0.0.1:8787. Нельзя выставлять встроенный HTTP-сервер напрямую в интернет. Нужны лимиты размера/времени запросов и per-IP rate limiting на proxy. Внутренний limiter активации за proxy общий: 15 попыток/5 минут.
4. Отдельный токен BotFather в APPSTORE_BOT_TOKEN и ссылка поддержки. Токен не коммитить и не публиковать. Рекомендуется новый бот для проверки, чтобы не перехватывать updates текущего Mini App.
5. Готовые клиентские сертификаты либо API поставщика регистрации. Регистрация UDID, платёжный шлюз, автоматическое получение p12 от стороннего бота и live Apple revocation API НЕ подключены.

Сервис: `python service.py serve`. Бот: `python bot.py` в другом процессе с теми же переменными среды. Polling не требует публичного webhook; работает, пока включён ПК. После выключения ПК новые активации и выдача ссылок не обслуживаются. Для круглосуточного сервиса нужен постоянно работающий хост.

## Подготовка одного клиента

Все файлы сертификата и bootstrap держать вне git checkout. Пример команды (параметры заменить реальными):

```bash
python service.py provision --telegram-id 123456789 \
  --device-id DEVICE_UDID --p12 /private/client.p12 \
  --profile /private/client.mobileprovision --password-file /private/password.txt \
  --ends 2027-01-01T00:00:00Z --endpoint https://activation.example.com \
  --out /private/StoreActivation.json
python personalize.py /private/AppStore-Plus-unsigned.ipa \
  /private/StoreActivation.json /private/AppStore-Plus-personal.ipa
```

После этого подписать персональную IPA соответствующим сертификатом существующим инструментом. Загрузить в ПРИВАТНОЕ хранилище и сформировать адрес установки, затем:

```bash
python service.py set-install-url ACCOUNT_ID https://your-domain.example/install/PERSONAL_LINK
```

Клиент вызывает /install и получает только свою ссылку. Подписанная сборка содержит activation code, но не p12/пароль. Ресурс нельзя считать нераспаковываемым секретом: персональная ссылка и IPA должны быть закрыты от посторонних. Код действует семь дней и привязывается к первому ключу; скопированный до привязки ресурс может быть украден. При таком инциденте требуется перевыпуск, не обещать hardware attestation. Реальное ограничение установки на устройство обеспечивается provisioning profile; App Attest пока не реализован.

Доступ начинается в момент provisioning; срок меньше либо равен реальному сроку сертификата/профиля. Его нельзя показывать как гарантию отсутствия отзывов Apple. `python service.py revoke ACCOUNT_ID` отключает сервисную сессию, но не отзывает сертификат у Apple и не удаляет установленные приложения.

## Проверки

`python -m unittest discover -s tests -v`

В этой среде доступны локальные проверки Python и протокола. Swift/iOS не компилировались: нужна согласованная macOS-сборка и проверка на iPhone. Платежи, выдача сертификатов поставщиком, подписывание персональной IPA и публикация пользователям требуют отдельных интеграций.

## One_iBot: получение уже выпущенного сертификата

Добавлен собственный адаптер `one_provider.py`, основанный на наблюдаемом контракте открытого клиента AppleEcosystem/oneAPi, ревизия `9efc56ab64dbb9eabc3c031188df4a593ec5b027` (25 июля 2025). Код стороннего проекта не переносился. Работоспособность старого API вживую не проверена.

Это отдельный API провайдера сертификатов, не Telegram `api_id/api_hash` и не BotFather token. Ключ провайдера нужен только на вашем сервере/ПК в `ONE_IBOT_API_KEY`; он не включается в IPA или bootstrap. До получения официального доступа к провайдеру существующий ручной `provision` с готовой парой сертификатов остаётся рабочим тестовым путём.

Адаптер делает только `GET /certificate?udid=...` с заголовком Authorization. Покупки, регистрация UDID (`POST /register`), платежи, отправка сообщений и публикация IPA не реализованы и автоматически не вызываются. Адрес API `https://api.bot1.org` взят из старого клиента; перед живым подключением подтвердить у провайдера актуальный origin и контракт.

После локальной настройки ключа ответ можно получить так (только при наличии разрешённого API-доступа):

```bash
python one_provider.py --udid DEVICE_UDID --out /private/one-response.json
python service.py provision-one --telegram-id 123456789 \
  --device-id DEVICE_UDID --response /private/one-response.json \
  --ends 2027-01-01T00:00:00Z --endpoint https://activation.example.com \
  --out /private/StoreActivation.json
```

Далее персонализация unsigned IPA выполняется той же командой `personalize.py`, после неё нужна настоящая подпись IPA и установка. При отсутствии поля `p12_password` укажите `--password-file /private/password.txt`; пароль не считается равным `1` автоматически. Сертификат и профиль декодируются и проверяются до записи в базу; сроки доступа не должны превышать реальный срок сертификата/профиля. Неоднозначный ответ для одного UDID, чужой UDID, незавершённая выдача, испорченный base64 и неверный пароль не активируются.

JSON провайдера содержит приватный ключ и пароль: держать вне git, не отправлять в чат, не размещать в публичном GitHub Releases. GitHub Releases остаётся выбранным местом для общих IPA каталога; персональный bootstrap и установочные пакеты требуют отдельной закрытой выдачи.

Это интеграция получения сертификата для существующего локального движка подписи. Серверная подпись произвольных приложений каталога и её очередь пока отсутствуют. Swift не изменялся этой правкой и не компилировался. 22 офлайн-проверки проходят, включая реальный тестовый P12/CMS, локальный HTTP протокол, изоляцию получателей бота, отказы провайдера и сохранение IPA при персонализации.

## Бот принимает файлы и сам выдаёт AppStore+

Новый тестовый сценарий описан в `DELIVERY-BOT.md`. Запуск — `python delivery_bot.py` вместо простого бота статусов. Он принимает пару сертификатов и пароль, определяет единственный UDID из профиля и автоматически готовит персональную установку. Альтернатива — существующий сертификат по UDID через API провайдера. Для HTTPS-выдачи `service.py serve` подключает маршруты /delivery/* при настройке APPSTORE_UNSIGNED_IPA и APPSTORE_ORIGIN. Сервис не развёрнут; настоящая подпись и iPhone требуют живого теста.
